# T13.3.28 — Production deployment closure

T13.3.28 is a bounded deployment-reliability release created after the first real Supabase fresh-install attempt exposed a schema/seed mismatch. It does not add customer features, redesign the application or activate POS/Web Till.

## Corrected

- Fresh `menu_items` schema now contains the `available` column required by `seed.sql`.
- Fresh schema and production seed are applied atomically so a seed failure cannot leave the base public schema committed by itself.
- Production backend commissioning rehearses the exact fresh/upgrade path on PostgreSQL 16 before a mutating production database run.
- The baseline regression suite uses the canonical fresh definition: schema + seed, followed by the ordered 107-migration chain.
- Production Edge Function secret validation includes `ABUSE_HMAC_SECRET`.
- Database commissioning no longer self-certifies the later live RLS gate.
- First `fresh` commissioning ends as an honest installation/bootstrap handoff; identity-dependent RLS, forms and e-mail acceptance run after owner/store/MFA bootstrap.
- Public-form and Turnstile live probes use current privacy-notice evidence and valid request shapes.
- Live RLS acceptance uses MFA/AAL2 for privileged roles and exact store/self ownership assertions.
- POS behavioural checks are removed from public-web live acceptance; POS remains deferred and undeployed.
- Two stale source verifiers were updated to test the current behaviour rather than obsolete source wording.
- GitHub production commissioning is restricted to `main`, refuses a stale committed source manifest, and mutating modes always deploy the fixed 14-function public set.
- The production preflight fails early if opaque `sb_publishable_*` / `sb_secret_*` values are placed into the existing legacy JWT-key variables; the broader Supabase key-model migration is intentionally outside this bounded patch.
- Successful synthetic public-form probes remove their matching queued notification jobs before deleting the test contact row, minimising the chance of a deployment probe producing real mail.
- The protected first frontend release explicitly handles the absence of a previous MilkPop live site while keeping all new-live owner/MFA checks mandatory.
- A guarded one-time recovery SQL file is supplied for the known partial fresh-install incident; it refuses unexpected tables, migration history, real business data or CV objects.
- Operator guidance now describes the Supabase Session Pooler path used by GitHub Actions.

## Unchanged

- 107 ordered upgrade migrations / 109 fresh-install SQL entries.
- 17 Edge Function sources / 14 public website-staff functions deployed.
- Three POS functions remain undeployed.
- Existing customer, staff, manager and owner product scope.
- Existing Supabase + Netlify + GitHub Actions architecture; no new production service is introduced.
